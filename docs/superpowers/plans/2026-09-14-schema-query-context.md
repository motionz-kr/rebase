# 스키마별 쿼리 입력 및 실행 컨텍스트 수정 계획

## 목표

- 데이터베이스(스키마) 우클릭 메뉴의 최상단에서 해당 DB를 선택한 쿼리 입력 상태로 진입한다.
- 다른 DB의 테이블에서 `최근 500개 조회`를 실행하면 SQL 에디터의 선택 DB와 실제 실행 DB가 해당 DB로 일치한다.
- 기존 연결/쿼리/테이블 보기 흐름과 다중 연결 상태 보존을 깨뜨리지 않는다.

## 설계

1. `SchemaExplorer`가 DB 우클릭 시 `onOpenQuery(db)`를 호출할 수 있도록 콜백을 추가하고, 컨텍스트 메뉴 첫 항목에 `쿼리 입력`을 배치한다.
2. `App`의 SQL 쿼리 요청에 대상 DB를 포함한다. 쿼리 입력은 자동 실행하지 않고, 최근 500개 조회는 SQL 로드와 실행을 함께 요청한다.
3. `QueryEditor`가 연결 프로필의 초기 DB와 별도로 현재 선택 DB를 상태로 관리한다. DB 전환 요청을 받으면 자동완성 스키마를 다시 불러오고, 쿼리 에디터 헤더·위험도 분석·편집 테이블 보기에 같은 DB를 사용한다.
4. Electron preload/main을 통해 실행 요청의 DB를 엔진으로 전달한다. 엔진은 요청 단위로 프로필의 DB를 덮어쓴 실행 프로필을 사용해 선택 DB에서 쿼리를 실행한다. SQLite는 파일 DB 특성상 기존 프로필 DB를 유지한다.

## 테스트 전략

- RED: 쿼리 요청 생성/대상 DB 전달을 순수 helper 테스트로 고정한다.
- GREEN: renderer와 Electron/engine 전달 경로를 구현하고 기존 테스트를 통과시킨다.
- `pnpm --filter renderer test` 및 관련 desktop 빌드/테스트를 실행한다.
- 실제 앱을 실행해 DB 우클릭 → 쿼리 입력, 다른 DB 테이블 우클릭 → 최근 500개 조회 흐름을 Playwright 또는 CDP로 검증한다. 테스트 DB가 없으면 저장소 규칙에 따라 우아하게 건너뛴다.

## 완료 조건

- DB 우클릭 메뉴 첫 항목이 `쿼리 입력`이고 클릭 시 해당 DB가 쿼리 에디터에 표시된다.
- 다른 DB 테이블에서 최근 500개 조회 시 에디터 헤더와 실제 실행 DB가 모두 대상 DB다.
- 기존 단위 테스트, 빌드, 핵심 E2E가 통과한다.
